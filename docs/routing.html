Routing & Failover

How requests get routed, what happens when providers fail, and why your users never see the 429.

How Routing Works

Every API key is linked to a provider. When you send a request:

  1. KeyParty decrypts your API key
  2. Looks up which provider that key belongs to
  3. Forwards the request to that provider

That's it. No magic. If you have 3 Groq keys, they all route to Groq. If you want Gemini, use a Gemini key.

Model Routing

Two ways to specify the model:

  • In the request body: "model": "groq/llama-3.3-70b-versatile" — KeyParty parses the provider prefix
  • Via headers: X-Gateway-Provider: groq + X-Gateway-Model: llama-3.3-70b-versatile — overrides everything
Pro tip: Use the header approach. It lets you change providers without touching your app code. Great for A/B testing.

Failover

When a provider returns 402 (quota exhausted) or 429 (rate limited), KeyParty can automatically reroute to a backup provider.

Configuration

SettingDescriptionDefault
failover_enabledEnable/disable failoverfalse
failover_providerBackup provider sluggemini
failover_modelBackup model namegemini-2.5-flash
failover_compactSummarize chat history on failovertrue
failover_triggersHTTP status codes that trigger failover402,429

Via Dashboard

Go to Settings tab in the dashboard. Toggle failover on, pick your backup provider and model, done.

Via API

curl -X PUT http://localhost:8080/admin/settings \
  -H "Authorization: Bearer your-admin-password" \
  -H "Content-Type: application/json" \
  -d '{
    "failover_enabled": true,
    "failover_provider": "gemini",
    "failover_model": "gemini-2.5-flash",
    "failover_compact": true,
    "failover_triggers": "402,429"
  }'

Request → Groq → 429 (rate limited)

    ▼
┌─────────────────┐
│ Failover enabled? │── no ── return error to client
└────────┬────────┘
         │ yes
         ▼
┌─────────────────┐
│ Compact enabled? │── no ── retry with backup provider
└────────┬────────┘
         │ yes
         ▼
┌─────────────────┐
│ Summarize chat   │ ── send history to backup model
│ history          │     get condensed summary
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│ Retry with       │ ── send summarized history + new message
│ backup provider  │
└─────────────────┘

Compaction

When failover triggers with compaction enabled:

  1. Your full chat history is sent to the backup model
  2. The backup model summarizes it into ~200 tokens
  3. The summarized history is sent to the backup provider
  4. Your conversation continues seamlessly

The compacted result is cached to avoid re-summarizing the same conversation.

Note: Compaction means some context is lost. The summary captures the gist, not every detail. For critical conversations, consider disabling compaction.

Provider Headers

Override routing per-request without changing your app:

HeaderDescriptionExample
X-Gateway-ProviderForce a specific providergemini
X-Gateway-ModelOverride the model namegemini-2.5-flash

When these headers are present, the model field in the request body is ignored.

Request Queuing

When a provider returns 429 and failover is disabled, KeyParty can queue the request and retry automatically.

Request → Groq → 429
    │
    ▼
┌─────────────────┐
│ Queue request     │ ── store in DB with retry count
└────────┬────────┘
         │
    (exponential backoff)
         │
         ▼
┌─────────────────┐
│ Retry request     │ ── 5s, 15s, 45s, 135s...
└────────┬────────┘
         │
    max retries hit?
         │ yes
         ▼
┌─────────────────┐
│ Return 429       │
│ to client        │
└─────────────────┘

Queue Configuration

View queue status:

curl http://localhost:8080/admin/queue \
  -H "Authorization: Bearer your-admin-password"

Semantic Cache

Similar prompts can be cached using embedding-based similarity matching. If two prompts are semantically similar, the cached response is returned without hitting the provider.

curl http://localhost:8080/admin/semantic-cache \
  -H "Authorization: Bearer your-admin-password"

A/B Testing

Send the same prompt to two providers and compare responses side by side.

curl -X POST http://localhost:8080/admin/ab-test \
  -H "Authorization: Bearer your-admin-password" \
  -H "Content-Type: application/json" \
  -d '{
    "prompt": "Explain quantum computing in simple terms",
    "provider_a": "groq",
    "model_a": "llama-3.3-70b-versatile",
    "provider_b": "gemini",
    "model_b": "gemini-2.5-flash"
  }'

Vote on the better response:

curl -X POST http://localhost:8080/admin/ab-test/vote \
  -H "Authorization: Bearer your-admin-password" \
  -H "Content-Type: application/json" \
  -d '{"test_id": "1", "winner": "a"}'

Health Dashboard

Real-time provider health metrics — uptime, latency percentiles, error rates.

curl http://localhost:8080/admin/health-dashboard \
  -H "Authorization: Bearer your-admin-password"

Response includes p50/p95/p99 latency, error rates, and uptime percentage per provider.
